## Le trio dangereux

Un agent devient vraiment dangereux quand il réunit trois capacités à la fois :

1. l'accès à des **données privées** (e-mails, documents, base clients) ;
2. l'exposition à du **contenu non fiable** (e-mails reçus, pages web, documents partagés, résultats d'outils tiers) ;
3. un moyen de **communiquer vers l'extérieur** ou d'agir (envoyer, payer, publier, appeler une URL).

Avec les trois, une injection peut faire fuiter des données ou déclencher une action. Retirer **une** des trois branches suffit souvent à casser l'attaque. C'est le principe du **moindre privilège** : chaque agent n'a que les outils et les droits strictement nécessaires à sa tâche.

## Les garde-fous

- **Contraintes dans les outils** : liste blanche de destinataires ou de domaines, plafonds de montant, périmètre de données limité à l'utilisateur authentifié. Le modèle peut demander ce qu'il veut, l'outil refuse.
- **Humain dans la boucle** pour les actions irréversibles ou coûteuses : paiement, suppression, envoi externe, avec un affichage clair de ce qui va être fait.
- **Séparer instructions et contenu** : baliser les données externes et rappeler qu'elles ne contiennent pas d'ordres. Utile, mais jamais suffisant seul.
- **Bac à sable** pour l'exécution de code, sans accès réseau ni secrets.
- **Journalisation** de chaque appel d'outil, alertes et limites de débit.

La solution la plus sûre (lecture seule) rend l'agent inutile ; retirer complètement le paiement casse une tâche légitime. Le bon compromis protège **les actions**, pas le modèle : l'envoi contraint côté outil, et le paiement soumis à un humain qui voit l'IBAN.

## Dans le code

```python
DOMAINES_AUTORISES = {"datamine.fr"}

def envoyer_email(destinataire: str, sujet: str, corps: str, contexte: Contexte) -> dict:
    domaine = destinataire.rsplit("@", 1)[-1].lower()
    if destinataire != contexte.expediteur_du_fil and domaine not in DOMAINES_AUTORISES:
        journal.alerte("envoi_refuse", destinataire=destinataire, session=contexte.session)
        return {"erreur": "Destinataire non autorisé pour cet agent."}
    return messagerie.envoyer(destinataire, sujet, corps)

def payer_facture(iban: str, montant: float, contexte: Contexte) -> dict:
    if montant > 5_000:
        return {"erreur": "Montant au-delà du plafond de l'agent."}
    demande = validation_humaine.creer(action="paiement", iban=iban, montant=montant, session=contexte.session)
    return {"statut": "en attente de validation humaine", "demande": demande.id}
```

La règle de sécurité doit venir d'une source **que ni le modèle ni le contenu lu ne peuvent modifier** : le code ou la configuration du serveur. Une liste fournie dans les arguments, demandée au modèle ou extraite d'un e-mail serait sous le contrôle de l'attaquant dès que l'injection réussit.

Même un faible taux de réussite d'une attaque devient inquiétant à grande échelle. Si chaque tentative réussit avec une probabilité $p$, la probabilité d'au moins un succès sur $n$ tentatives vaut :

$$
P(\geq 1 \text{ succès}) = 1 - (1 - p)^n
$$

<Exercise

  question="Une injection réussit dans 2 % des cas. L'agent reçoit 50 e-mails piégés par mois. Probabilité d'au moins une attaque réussie dans le mois (3 décimales) ?"
  answer={0.636}

  hint="1 − 0,98 puissance 50."
>
$1 - 0{,}98^{50} \approx 0{,}636$ : presque deux chances sur trois chaque mois. Un garde-fou probabiliste (« le modèle résiste presque toujours ») ne suffit pas contre un attaquant qui peut réessayer ; il faut des barrières qui bloquent **à coup sûr** les conséquences graves.
</Exercise>

<Callout type="intuition">
Traite le modèle comme un **stagiaire très doué mais manipulable** qui lit tout ce qui passe : tu ne lui confies pas la carte bancaire de l'entreprise sans plafond ni validation, et tu ne lui donnes pas accès à des dossiers dont il n'a pas besoin. Les contrôles d'accès se font au niveau des systèmes, pas de ses bonnes intentions.
</Callout>

<Callout type="piege">
Les sources d'injection sont partout : pages web consultées, documents d'un RAG, résultats d'un outil tiers, descriptions d'outils d'un serveur MCP non audité, noms de fichiers, métadonnées d'images. Et les **secrets** (clés d'API, mots de passe) ne doivent jamais apparaître dans le contexte : ce que le modèle voit, une injection peut le lui faire répéter.
</Callout>

<Callout type="entretien">
Question classique : « Comment sécuriser un agent qui navigue sur le web et a accès aux données de l'entreprise ? » Réponse structurée : moindre privilège (séparer l'agent qui lit le web de celui qui accède aux données sensibles), contraintes déterministes dans les outils, validation humaine des actions irréversibles, bac à sable, pas de secrets dans le contexte, journalisation et détection d'anomalies, tests d'attaque (red teaming) intégrés à l'évaluation.
</Callout>

<Callout type="astuce">
Ajoute des **cas d'attaque** à ton banc d'évaluation (e-mails piégés, documents empoisonnés, demandes hors périmètre) et suis leur taux de blocage à chaque version, comme une métrique de qualité. Un agent qui progresse en utilité mais régresse en sécurité ne doit pas partir en production.
</Callout>

## En entretien

<Interview q="Comment protèges-tu un agent contre l'injection de prompt ?">
Je pars du principe que l'injection finira par réussir sur le modèle, et je limite ses conséquences. Moindre privilège : l'agent n'a que les outils et les données nécessaires, et j'évite de réunir accès aux données privées, contenu non fiable et capacité d'exfiltration dans le même agent. Contraintes déterministes dans les outils : destinataires autorisés, plafonds, périmètre de l'utilisateur. Validation humaine des actions irréversibles, avec un affichage explicite. Séparation balisée des contenus externes, en complément. Bac à sable pour le code, aucun secret dans le contexte, journalisation, limites de débit et alertes. Et des cas d'attaque dans le banc d'évaluation, suivis à chaque version.
</Interview>

<Interview q="Quand faut-il un humain dans la boucle d'un agent ?">
Pour les actions irréversibles ou à fort impact (paiements, suppressions, envois externes, modifications en production), pour les cas où l'agent est peu confiant ou hors de son périmètre, et au début d'un déploiement, le temps de mesurer la fiabilité réelle. La validation doit être utile : présenter précisément l'action, ses paramètres et la raison, sans noyer l'humain sous des demandes (sinon il finit par tout approuver). On assouplit ensuite par paliers, sur les catégories d'actions dont le taux d'erreur mesuré est acceptable.
</Interview>

<Recap>
- **Injection indirecte** : instructions cachées dans un contenu lu par l'agent.
- **Trio dangereux** : données privées + contenu non fiable + capacité d'agir vers l'extérieur.
- **Moindre privilège** ; contraintes **dans les outils** (liste blanche, plafonds, périmètre).
- **Humain dans la boucle** pour les actions irréversibles ; bac à sable ; aucun secret dans le contexte.
- Consigne dans le prompt : utile, jamais suffisante.
- À l'échelle : $1 - (1-p)^n$ ; il faut des barrières déterministes.
- Cas d'attaque dans le banc d'évaluation.
</Recap>
