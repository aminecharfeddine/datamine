## Le principe du k-fold

On découpe les données en $k$ parts égales, les **plis** (*folds*). Puis on répète $k$ fois :

1. on met un pli de côté pour la validation ;
2. on entraîne le modèle sur les $k-1$ autres ;
3. on mesure l'erreur sur le pli mis de côté.

L'estimation finale est la moyenne des $k$ erreurs :

$$
\text{CV}_k = \frac{1}{k}\sum_{f=1}^{k} \text{Erreur}\big(\text{modèle entraîné sans le pli } f,\ \text{pli } f\big)
$$

Chaque exemple est utilisé exactement une fois en validation. Dans le labo, choisis un degré de polynôme, puis compare la courbe de validation croisée à l'**erreur réelle**, mesurée sur des données neuves que le modèle ne verra jamais en pratique.

<CvLab id="choix" degree={10} k={5} challenge="cv-select" />

<Callout type="intuition">
Coche « 10 découpages simples » : chaque ligne grise désigne son propre meilleur degré. La validation croisée moyenne ces avis et donne une estimation bien plus stable, pour un coût de calcul $k$ fois plus élevé.
</Callout>

<Callout type="rappel">
Quel $k$ choisir ? $k = 5$ ou $10$ est le compromis habituel. **Leave-one-out** ($k = n$) utilise presque toutes les données pour entraîner, mais coûte $n$ entraînements et ses estimations sont plus variables. Pour la classification, on utilise des plis **stratifiés** : chaque pli garde la même proportion de classes que le dataset.
</Callout>

## Train, validation, test : trois rôles

Un projet bien mené sépare trois usages des données :

| Ensemble | Sert à | Utilisé |
|---|---|---|
| Entraînement | ajuster les paramètres du modèle | à chaque entraînement |
| Validation | choisir les hyperparamètres et le modèle | autant que nécessaire |
| Test | estimer la performance finale, de façon honnête | **une seule fois**, à la fin |

La validation croisée remplace le validation set fixe : on garde un test set à part, et sur le reste on fait des plis tournants. Une fois les hyperparamètres choisis, on **réentraîne** le modèle sur toutes les données d'entraînement avant de l'évaluer sur le test.

<Exercise
  id="grid"
  question="Tu testes 3 valeurs de λ et 4 profondeurs maximales, en validation croisée à 5 plis. Combien de modèles entraînes-tu pendant la recherche ?"
  answer={60}
  tolerance={0}
  hint="Une combinaison d'hyperparamètres = un entraînement par pli."
>
$3 \times 4 = 12$ combinaisons, chacune évaluée sur 5 plis : $12 \times 5 = 60$ entraînements.

On en ajoute un 61ᵉ pour réentraîner la meilleure combinaison sur toutes les données. C'est pour ce coût qu'on remplace souvent la grille complète par une **recherche aléatoire** ou bayésienne.
</Exercise>

## La fuite de données

La validation croisée ne protège que si **rien** de ce qui sert à construire le modèle n'a vu les données de validation. Sinon, c'est une **fuite de données** (*data leakage*) : l'information du test s'infiltre dans l'entraînement.

<Predict
  id="fuite"
  question="Sur des données de pur bruit (étiquettes au hasard), on garde les 20 variables les plus corrélées à l'étiquette sur TOUT le dataset, puis on fait une validation croisée. Quelle précision obtient-on ?"
  options={["Environ 50 %, comme le hasard", "Nettement plus que 50 %", "Moins de 50 %", "La validation croisée refuse de tourner"]}
  answer={1}
>
Parmi 2 000 variables de bruit, certaines sont corrélées à l'étiquette **par hasard**, y compris sur les exemples qui serviront ensuite de validation. Les sélectionner en regardant tout le dataset, c'est déjà avoir triché : le modèle « reconnaît » les plis de validation. Vérifie-le.
</Predict>

<LeakLab id="illusion" challenge="leak-illusion" />

Ce piège a réellement faussé des études publiées, notamment en génomique, où l'on a beaucoup de variables pour peu de patients. La règle est simple : **toute étape apprise à partir des données** fait partie du modèle et doit être refaite dans chaque pli.

- Sélection de variables.
- Normalisation et standardisation (moyenne et écart-type calculés sur le train seulement).
- Imputation des valeurs manquantes, encodage des catégories rares.
- Rééquilibrage des classes (*oversampling*), à faire **après** le découpage.

<Callout type="piege">
D'autres fuites sont plus sournoises. Une variable connue seulement **après** l'événement à prédire (« montant remboursé » pour prédire une fraude). Un même patient ou client présent à la fois en train et en test : on découpe alors **par groupe**. Des séries temporelles mélangées au hasard, où le modèle voit le futur : on valide alors dans l'ordre chronologique.
</Callout>

<Callout type="entretien">
Avec scikit-learn, la manière robuste est un `Pipeline` passé à `cross_val_score` ou `GridSearchCV` : chaque étape est réapprise automatiquement dans chaque pli. Et si l'on règle les hyperparamètres par validation croisée, l'estimation obtenue est elle-même légèrement optimiste : on garde un test set final, ou on fait une **validation croisée imbriquée** (*nested CV*).
</Callout>

## En entretien

<Interview q="Comment évites-tu le data leakage dans un pipeline de ML ?">
Trois réflexes. Un : je découpe **avant** tout traitement appris sur les données, et j'encapsule normalisation, imputation, sélection de variables et modèle dans un `Pipeline` passé à la validation croisée, pour que tout soit réappris dans chaque pli. Deux : je découpe selon la structure réelle du problème : par groupe (un patient, un client) avec `GroupKFold`, dans l'ordre du temps pour des données temporelles. Trois : je vérifie que chaque variable est disponible **au moment de la prédiction** en production. Et une performance « trop belle » déclenche toujours une enquête.
</Interview>

<Interview q="Qu'est-ce que la nested cross-validation, et quand l'utiliser ?">
Quand on règle les hyperparamètres par validation croisée, le score du meilleur réglage est optimiste : on a choisi le maximum parmi beaucoup d'essais. La CV imbriquée ajoute une boucle extérieure : chaque pli extérieur sert de test, et à l'intérieur, une CV choisit les hyperparamètres sur le reste. On obtient une estimation honnête de **toute la procédure** (réglage compris). Utile pour publier un résultat sur un petit dataset ; sur un gros dataset, un simple test set mis de côté suffit.
</Interview>

<Recap>
- k-fold : k entraînements, chaque exemple sert une fois en validation ; moyenne des k scores.
- k = 5 ou 10 en pratique ; plis stratifiés en classification ; par groupe ou chronologiques si nécessaire.
- Rôles : train (paramètres), validation (hyperparamètres), test (une fois, à la fin).
- Fuite de données : toute étape apprise sur les données doit être refaite dans chaque pli.
- Pipelines pour automatiser ; vérifier qu'aucune variable ne vient du futur.
- Score trop beau = suspicion de fuite.
</Recap>
